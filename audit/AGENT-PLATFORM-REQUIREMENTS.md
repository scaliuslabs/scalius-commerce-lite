## Release Rule

This is the exhaustive requirement-to-evidence checklist for the Admin Copilot and Storefront Shopping Assistant target. It rebaselines the larger product objective without rewriting the verified history in the remediation tracker.

A stable release requires every non-voice row to be `Verified` with the listed code, automated test, browser, deploy, and live evidence where applicable. Product scope may not be silently deferred. Voice rows are non-blocking while voice is disabled; every voice row becomes blocking if voice is enabled in production.

Status meanings:

- `Verified`: target-state acceptance evidence exists and was reviewed.
- `Baseline verified`: a safe current-state foundation exists, but it must be reverified after the target migration.
- `Partial`: meaningful implementation exists, but the stated requirement or evidence is incomplete.
- `Missing`: no implementation satisfying the target was found.
- `Optional — missing`: non-blocking only while the feature remains disabled.

An ADR, typecheck, or unit test alone cannot move a runtime row to `Verified`. Evidence entries describe the minimum proof; the final verification record must include dates, commands, deployed versions, and live/browser results in the remediation tracker or a successor release record.

## Evidence Update Rules

When implementation begins:

1. Update the relevant row in the same change that adds or verifies the capability; do not mark it `Verified` from intent or code review alone.
2. Link focused test files, migrations, routes, Workers, browser artifacts, deploy versions, and live/ops results rather than copying long logs into this document.
3. Keep historical current-state claims in the remediation tracker. This checklist records target closure, not a replacement history.
4. If a requirement is split, retain the original ID and add suffixed rows so traceability to the objective remains intact.
5. Any newly discovered capability, data class, provider side effect, or interaction mode must be classified for authority, permission, risk, confirmation, idempotency, concurrency, audit, privacy, accessibility, operations, and release evidence before exposure.

## Stable-Release Sign-Off

The final sign-off must name the reviewed commit, Admin Agent version, Storefront Agent version, API/Admin/Storefront versions, D1 migration versions, enabled provider profiles, enabled UCP/MCP capabilities, test and browser matrices, security/privacy review, performance/load report, live release check, ops check, rollback exercise, remaining known limitations, and approvers. Until that record exists and REL-015 is `Verified`, the full agent platform is not stable-release ready.
