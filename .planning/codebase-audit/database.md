# Database Schema & Migrations Audit

**Analysis Date:** 2026-03-20

## Summary

The database layer lives in `packages/database/` and comprises 13 schema files (11 domain + shared + enums), a D1 client factory, and 30 sequential SQL migrations (0000-0029). The schema covers ~40 tables across auth, products, orders, inventory, delivery, customers, marketing, content, RBAC, and system domains. FTS5 full-text search is layered on top via triggers.

**Overall assessment: Solid.** Consistent naming, comprehensive FK coverage, good index discipline, and standardized timestamp handling. The issues below are real but minor relative to the schema's overall quality.

---

## Critical Issues

### 1. Missing Drizzle Snapshots for Migrations 0019-0026

- **Files:** `packages/database/migrations/meta/` is missing `0019_snapshot.json` through `0026_snapshot.json`
- **Impact:** Drizzle Kit uses snapshots to compute diffs for `pnpm db:generate`. Missing snapshots mean Drizzle cannot reconstruct the schema state at those points, which can cause incorrect or duplicate diff output on the next `db:generate` run.
- **Root cause:** Migrations 0019-0026 were hand-written (index-only, data-only, ALTERs) rather than generated by `drizzle-kit generate`. The snapshots only exist for 0000-0018, 0027-0029.
- **Fix approach:** Run `drizzle-kit generate` against the current schema to re-sync the snapshot chain, or manually create placeholder snapshots matching the journal entries.

### 2. `permissions.updatedAt` is Nullable (Inconsistent with All Other Tables)

- **File:** `packages/database/src/schema/rbac.ts:21-22`
- **Schema definition:**
  ```typescript
  updatedAt: integer("updated_at", { mode: "timestamp" })
      .default(UNIX_NOW),  // Missing .notNull()
  ```
- **Impact:** Every other table in the schema marks `updatedAt` as `.notNull().default(UNIX_NOW)`. The `permissions` table omits `.notNull()`, making it nullable. This was added in migration 0024 as `ALTER TABLE permissions ADD COLUMN updated_at INTEGER;` (no NOT NULL, no DEFAULT).
- **Fix approach:** Add `.notNull()` to the schema definition. Since existing rows already have values (DEFAULT UNIX_NOW works on new inserts), backfill NULLs with `UPDATE permissions SET updated_at = created_at WHERE updated_at IS NULL`, then add the NOT NULL constraint via a table-recreate migration.

### 3. `discountUsage.customerId` FK Missing `onDelete` Behavior

- **File:** `packages/database/src/schema/marketing.ts:101`
- **Schema definition:**
  ```typescript
  customerId: text("customer_id").references(() => customers.id),
  // No onDelete specified -- defaults to "no action"
  ```
- **Impact:** If a customer is deleted, their discount usage records become orphaned with a dangling `customer_id`. Every other customer FK in the codebase uses `onDelete: "set null"` or `onDelete: "cascade"`.
- **Fix approach:** Add `{ onDelete: "set null" }` to match the pattern used by `orders.customerId`.

## Schema Quality

### Naming Conventions

**Table names:** Consistent snake_case in SQL, camelCase Drizzle exports. Pluralized for entity tables (`products`, `orders`, `categories`), compound names for junction tables (`discount_products`, `role_permissions`, `product_attribute_values`).

**Column names:** snake_case in SQL columns, camelCase in Drizzle TypeScript. Boolean columns use `is_` prefix (`is_active`, `is_published`, `is_super_admin`). FK columns use `_id` suffix (`product_id`, `order_id`, `customer_id`).

**Index names:** Descriptive `{table}_{column(s)}_idx` pattern. Unique indexes use `_unique_idx` or `_unique` suffix. Composite indexes name the purpose (`products_active_idx` for `(isActive, deletedAt)`).

### FK Relationships (43 total)

All FK columns have explicit `.references()` declarations with appropriate `onDelete` behavior:
- **`cascade`**: Used for child records that should die with the parent (order_items -> orders, widget_history -> widgets, etc.)
- **`set null`**: Used for optional associations (products.categoryId -> categories, orders.customerId -> customers, etc.)
- **Exception:** `discountUsage.customerId` has no `onDelete` specified (defaults to "no action") -- see Critical Issue #3 above.

### Self-Referential FKs

Two tables use self-referential FKs with the required `(): any =>` escape hatch for Drizzle's type system:
- `packages/database/src/schema/delivery.ts:14` -- `deliveryLocations.parentId` -> `deliveryLocations.id`
- `packages/database/src/schema/products.ts:203` -- `mediaFolders.parentId` -> `mediaFolders.id`

### Soft Delete Pattern

17 tables implement soft delete via a `deletedAt: integer("deleted_at", { mode: "timestamp" })` column: `products`, `product_variants`, `categories`, `collections`, `product_attributes`, `media_folders`, `media`, `orders`, `customers`, `discounts`, `pages`, `widgets`, `hero_sliders`, `delivery_locations`, `shipping_methods`, `checkout_languages`.

Tables that intentionally lack soft delete: auth tables, RBAC junction tables, `order_items`, `order_payments`, `inventory_movements`, `webhook_events`, `analytics`, `settings`, `site_settings`, `hero_sections`, `page_templates`.

### Singleton Pattern

Two tables enforce single-row semantics via a `singletonKey` column with a unique index:
- `packages/database/src/schema/system.ts:28` -- `site_settings.singleton_key` with `uniqueIndex("site_settings_singleton_idx")`
- `packages/database/src/schema/marketing.ts:112` -- `meta_conversions_settings.singleton_key` with `uniqueIndex("meta_conversions_settings_singleton_idx")`

### Optimistic Locking

Two tables use version columns for CAS (Compare-and-Swap) operations:
- `packages/database/src/schema/orders.ts:49` -- `orders.version` (general order updates)
- `packages/database/src/schema/products.ts:72-74` -- `product_variants.version` (general updates) + `product_variants.stockVersion` (stock-specific CAS, separate from general version)

## Migration Quality

### Overview (30 migrations, 0000-0029)

| Category | Migrations | Notes |
|----------|------------|-------|
| Initial schema | 0000 | Creates all original tables (~476 lines) |
| Auto-generated (Drizzle) | 0001-0013, 0015, 0017-0018, 0027-0029 | Standard Drizzle-generated DDL |
| Hand-written (indexes) | 0019, 0023, 0025 | Index-only, all use `IF NOT EXISTS` |
| Hand-written (data) | 0014, 0024, 0026 | Data migrations + schema fixes |
| Hand-written (columns) | 0020, 0021, 0022 | Simple ALTER TABLE ADD COLUMN |
| FTS5 setup | 0016 | Full-text search tables + triggers |
| No-op sync | 0027 | `SELECT 1;` to sync Drizzle snapshot state |

### Idempotency

- **Hand-written index migrations (0019, 0023, 0025, 0029):** All use `CREATE INDEX IF NOT EXISTS` -- safe for re-runs.
- **Hand-written data migrations (0014, 0024, 0026):** Use `WHERE` guards (e.g., `WHERE phone LIKE '01%' AND LENGTH(phone) = 11`) -- safe for re-runs.
- **FTS5 migration (0016):** Uses `DROP TABLE IF EXISTS` and `DROP TRIGGER IF EXISTS` before creation -- safe.
- **Auto-generated migrations:** Standard Drizzle output. Not inherently idempotent (no IF NOT EXISTS on CREATE TABLE). This is expected -- Drizzle tracks applied migrations.

### PRAGMA foreign_keys Concern

Migration 0028 (`0028_loving_steel_serpent.sql`) uses the table-recreate pattern with `PRAGMA foreign_keys=OFF` at line 7 and `PRAGMA foreign_keys=ON` at the end. This is correct for SQLite table recreations. However, if the migration fails partway through, FK enforcement remains off for the D1 connection.

- **Impact:** Low for D1 (each request gets a fresh connection), but worth noting.
- **Files affected:** `packages/database/migrations/0028_loving_steel_serpent.sql`

### Legacy `CURRENT_TIMESTAMP` in Early Migrations

The initial migration (0000) uses `DEFAULT CURRENT_TIMESTAMP` for many tables (categories, collections, customer_history, customers, delivery_*, hero_*, pages, etc.), while newer tables in the same migration use `DEFAULT (cast(strftime('%s','now') as int))`.

- **Impact:** Tables created from migration 0000 that were never recreated still have `CURRENT_TIMESTAMP` as the SQL default. This stores ISO-8601 strings into integer columns. Drizzle's `{ mode: "timestamp" }` then interprets these as epoch seconds, producing incorrect Date objects (year ~55000+).
- **Mitigation:** All runtime inserts go through Drizzle ORM which uses the TypeScript schema's `UNIX_NOW` default, so this only affects rows inserted via raw SQL or SQLite defaults triggered by non-Drizzle paths. The risk is low but nonzero.
- **Tables with legacy CURRENT_TIMESTAMP defaults (not yet migrated to UNIX_NOW):** `categories`, `collections`, `customer_history`, `customers`, `delivery_locations`, `delivery_providers`, `hero_sections`, `hero_sliders`, `page_templates`, `pages`, `product_attribute_values`, `product_attributes`, `product_images`, `product_rich_content`, `products`, `settings`.

### Missing Meta Snapshots

Migrations 0019-0026 (hand-written) have no corresponding `meta/{idx}_snapshot.json` files. The journal (`meta/_journal.json`) references all 30 migrations, but the snapshot chain jumps from 0018 to 0027.

### Stale Data Migration Script

`packages/database/migrations/migrate-collections-data.ts` references `@libsql/client/web` (Turso) and `TURSO_DATABASE_URL` -- leftover from the pre-D1 era. This script is no longer functional since the project migrated to Cloudflare D1.

## Type Safety & Consistency

### Primary Keys

All tables use `text("id").primaryKey()` with UUIDs generated at the application layer. No auto-incrementing integer PKs.

- **Implication:** Join performance is slightly worse than integer PKs in SQLite, but the trade-off is acceptable for distributed ID generation (no single-writer bottleneck on D1).

### Timestamp Handling

All timestamp columns use `integer("...", { mode: "timestamp" })` with `UNIX_NOW` default (epoch seconds). This is consistent across all 13 schema files.

- **`createdAt`**: Present on all 40 tables, always `.notNull().default(UNIX_NOW)`.
- **`updatedAt`**: Present on 37 tables. Missing on: `inventoryMovements` (append-only), `webhookEvents` (append-only), `metaConversionsLogs` (append-only). These omissions are intentional for append-only audit tables.
- **Exception:** `permissions.updatedAt` is nullable (see Critical Issue #2).

### Enum-like Text Columns

The schema uses two patterns for constrained text values:

**1. TypeScript const objects (in `enums.ts`):**
```typescript
export const OrderStatus = { PENDING: "pending", ... } as const;
export type OrderStatus = (typeof OrderStatus)[keyof typeof OrderStatus];
```
Used for: `OrderStatus`, `PaymentMethod`, `PaymentStatus`, `FulfillmentStatus`, `InventoryPool`, `ItemFulfillmentStatus`, `DeliveryProvider`, `DiscountType`, `DiscountValueType`, `WidgetPlacementRule`.

**2. Inline Drizzle `enum` option:**
```typescript
type: text("type", { enum: ["city", "zone", "area"] }).notNull(),
```
Used for: `deliveryLocations.type`, `customerHistory.changeType`, `heroSliders.type`, `productVariants.barcodeType`, `products.discountType`, `widgets.displayTarget`, `siteSettings.authVerificationMethod`, `siteSettings.checkoutMode`, `metaConversionsLogs.status`, `discountProducts.applicationType`.

**Inconsistency:** Some status/type columns reference the TypeScript enum objects in their JSDoc comments but use bare `text()` in the schema (e.g., `orders.status`, `orderPayments.status`, `codTracking.codStatus`). These columns have no compile-time type narrowing -- they accept any string.

### JSON-in-Text Columns (18 columns)

These columns store JSON as plain `text()` with no `{ mode: "json" }` typing (except `productAttributes.options`):

| Table | Column | Content |
|-------|--------|---------|
| `collections` | `config` | Category/product IDs, display config |
| `delivery_locations` | `external_ids` | Provider-specific location mappings |
| `delivery_locations` | `metadata` | Location metadata |
| `delivery_providers` | `config` | Provider configuration |
| `delivery_shipments` | `metadata` | Shipment details |
| `delivery_shipments` | `shipment_items` | Item list per shipment |
| `site_settings` | `header_config` | Header layout JSON |
| `site_settings` | `footer_config` | Footer layout JSON |
| `site_settings` | `social_links` | Social media URLs |
| `site_settings` | `contact_info` | Contact details |
| `analytics` | `config` | Analytics provider config |
| `checkout_languages` | `language_data` | Translation strings |
| `checkout_languages` | `field_visibility` | Field visibility settings |
| `hero_sections` | `config` | Hero display config |

Only `product_attributes.options` uses `text("options", { mode: "json" }).$type<string[]>()` for typed JSON parsing.

- **Impact:** All other JSON columns are treated as opaque strings by Drizzle. Parsing happens at the service layer. This is pragmatic but means no schema-level validation of JSON structure.

### Drizzle Relations

**Not defined.** The schema uses inline `.references()` for FK constraints but does not define Drizzle `relations()` objects. This means:
- No `db.query.orders.findMany({ with: { items: true } })` syntax available
- All JOINs must be written manually via `db.select().from().leftJoin()`
- The relational query API is unavailable

This is a deliberate trade-off -- the codebase uses explicit JOINs everywhere.

### Type Exports

Every schema file exports `InferSelectModel` types:
```typescript
export type Product = InferSelectModel<typeof products>;
```

No `InferInsertModel` types are exported. Insert types are inferred at call sites or via Zod validation schemas in `packages/core/src/modules/*/`.

## Scalability Concerns

### 1. Unbounded Audit Tables

`inventory_movements`, `webhook_events`, and `meta_conversions_logs` grow indefinitely with no retention policy at the schema level.

- `inventory_movements`: One row per stock change (reserved, deducted, released, adjusted). High-volume stores generate thousands per day.
- `webhook_events`: One row per incoming webhook from payment/delivery providers.
- `meta_conversions_logs`: One row per Meta Conversions API event. Has `log_retention_days` setting (default 30) but no automatic cleanup.
- **Mitigation path:** Add a scheduled cleanup job (Cloudflare Cron Trigger) that deletes records older than N days.

### 2. FTS5 Trigger Overhead

Every INSERT, UPDATE, and DELETE on the 8 FTS-indexed tables fires 2 triggers (before+after for updates). For batch operations (e.g., `handleOrderIngestBatch` processing multiple orders in one queue message), this adds overhead per row.

- **Tables with FTS triggers:** `products`, `product_variants`, `categories`, `pages`, `orders`, `customers`, `discounts`, `abandoned_checkouts`
- **Mitigation:** D1 handles this well for single-tenant, but batch inserts will be slower than non-FTS tables.

### 3. `deliveryLocations` Tree Queries

The self-referential `parent_id` FK creates a city/zone/area hierarchy. SQLite has no native recursive CTE optimization. Deep tree queries require multiple round-trips or application-level recursion.

- **File:** `packages/database/src/schema/delivery.ts:9-28`
- **Mitigation:** `delivery_locations.parent_id` has an index (added in migration 0023). The hierarchy is typically 3 levels deep (city -> zone -> area), so this is manageable.

### 4. Denormalized Customer Data on Orders

`orders` stores `customerName`, `customerPhone`, `customerEmail`, `shippingAddress`, `city`, `zone`, `area`, `cityName`, `zoneName`, `areaName` -- a full snapshot of customer data at order time. This is intentional (order data should not change when customer updates their profile), but it means order searches by customer data require scanning these denormalized columns rather than a single JOIN.

- **File:** `packages/database/src/schema/orders.ts:21-30`
- **Mitigation:** FTS5 index on `orders_fts(customer_name, customer_phone, order_id)` handles search. The `orders.customer_id` FK + index enables customer-to-orders lookups.

## LLM-Friendliness

### Strengths

1. **Clear domain separation:** 13 files with descriptive names (`auth.ts`, `orders.ts`, `inventory.ts`). An LLM can locate any table's schema in 1 file read.

2. **Comprehensive JSDoc comments:** Enum columns include `/** Valid: ... */` comments documenting allowed values (e.g., `orders.ts:34-35`, `orders.ts:39`, `orders.ts:43-44`).

3. **Barrel export in `index.ts`:** Single import point for all schema symbols.

4. **Type exports alongside tables:** Every table definition is followed by its `InferSelectModel` type export.

5. **Shared constants are centralized:** `UNIX_NOW` in `shared.ts`, all enum objects in `enums.ts`.

6. **`enums.ts` is self-documenting:** Each enum has both a value object and a TypeScript type with the same name.

### Weaknesses

1. **No entity relationship documentation:** There is no ER diagram or relationship summary in the schema files. An LLM must trace `.references()` calls across files to understand the data model.

2. **JSON column shapes are undocumented:** 18 text columns store JSON with no inline type annotation or comment describing the expected structure (e.g., what does `collections.config` contain?).

3. **Status machine transitions are not documented at the schema level:** The `orders.status` column accepts 11 values but the valid state transitions are defined elsewhere (`packages/core/src/modules/orders/order-state-machine.ts`).

4. **`media` and `mediaFolders` live in `products.ts`** rather than their own file, which is counterintuitive since media is shared across domains.

## Recommended Changes

### High Priority

1. **Fix `permissions.updatedAt` nullability** -- Add `.notNull()` in `packages/database/src/schema/rbac.ts:21`. Generate a migration that backfills NULLs and adds NOT NULL constraint.

2. **Add `onDelete: "set null"` to `discountUsage.customerId`** in `packages/database/src/schema/marketing.ts:101`. Generate a migration (requires table recreate since SQLite cannot ALTER FK constraints).

3. **Add missing `orders.deleted_at` index** -- Add `index("orders_deleted_at_idx").on(table.deletedAt)` in `packages/database/src/schema/orders.ts`. This is the only soft-deletable table without a deleted_at index.

4. **Re-sync Drizzle snapshots** -- Run `drizzle-kit generate` to create snapshot files for the 0019-0026 gap, ensuring future migrations generate correctly.

### Medium Priority

5. **Add `mediaFolders.parent_id` index** -- The self-referential FK has no index, making tree queries slower. Add `index("media_folders_parent_id_idx").on(table.parentId)` in `packages/database/src/schema/products.ts`.

6. **Standardize legacy `CURRENT_TIMESTAMP` defaults** -- 16 tables still have `CURRENT_TIMESTAMP` as the SQL-level default from migration 0000. A single migration can recreate these tables with `UNIX_NOW` defaults. Low urgency since Drizzle ORM always supplies the value, but eliminates a class of potential bugs.

7. **Delete stale `migrate-collections-data.ts`** -- This Turso-era script in `packages/database/migrations/` references `@libsql/client` which is no longer a dependency. It causes confusion.

### Low Priority

8. **Add Drizzle `relations()` definitions** -- Currently the schema has no relational query support. Adding `relations()` would enable `db.query.*.findMany({ with: ... })` syntax, reducing boilerplate JOINs in services.

9. **Type the JSON columns** -- Add `{ mode: "json" }.$type<T>()` to the 18 text columns that store JSON, providing type safety at the Drizzle layer.

10. **Add retention index to `inventory_movements`** -- Add a composite index on `(created_at, type)` to support efficient cleanup queries for the unbounded audit table.
