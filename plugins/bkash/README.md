# bKash for Scalius (`scalius.bkash`)

Take bKash payments at checkout through **bKash Tokenized Checkout** (API
v1.2.0-beta). Buyers pay on bKash's own page with their wallet number, OTP and
PIN; the order is marked paid only after bKash confirms the payment to
Scalius server to server. Refunds go back to the buyer's bKash wallet from the
order page.

It is a first-party app built only on the public plugin contract: a hosted
payment provider (`scalius.bkash:bkash`) on the platform's payment port.

## Set it up

1. **Get bKash payment gateway credentials.** bKash issues four values to a
   merchant with a Tokenized Checkout (PGW) account: an **app key**, an
   **app secret**, a **username** and a **password**. Sandbox and live have
   separate sets.
2. **Install and approve the app** in **Settings → Apps**. It asks for network
   access to bKash's two API hosts (`tokenized.sandbox.bka.sh`,
   `tokenized.pay.bka.sh`) and for nothing in your store.
3. **Fill in the app's settings**: choose **Sandbox** or **Live** under
   Environment and enter the four credentials. The secret and the password
   are stored encrypted and never shown again. Use **Test connection** to
   check them: it asks bKash for a token and reports the result.
4. **Enable bKash in Settings → Payments.** Checkout then offers "bKash" for
   orders in BDT.

There is nothing to configure at bKash: the callback URL that brings the buyer
back is generated by Scalius for every payment and sent with it.

## How a payment works

1. At checkout Scalius commits the order, then the app creates a bKash payment
   (`mode 0011`, `intent sale`) for the amount due, with Scalius's payment
   reference as bKash's merchant invoice number. A retry of the same checkout
   attempt gets the same bKash payment back, never a second one.
2. The buyer pays on bKash's page and bKash sends them back with the payment
   id and a status (`success`, `failure` or `cancel`).
3. The app never trusts that status. On `success` it calls bKash's **Execute**
   itself, which is what actually completes a Tokenized Checkout payment; for
   anything else (or an Execute bKash refuses) it asks bKash for the payment's
   status. Only bKash's own answer for a payment this app created counts, and
   its amount, currency and invoice number must match what was created.
4. A cancelled or failed payment releases the checkout attempt so the buyer
   can try again, and the app never executes that payment afterwards.
5. If the buyer's return is lost or bKash is slow, the platform asks the app
   for the payment's status later; the same capture always produces the same
   event (keyed by bKash's transaction id), so it is applied once.

## Refunds

Refund in full or in part from the order page; several partial refunds are
fine up to what was paid, as bKash allows. Each refund is recorded before it
is sent and is sent at most once, even if Scalius retries. If bKash's answer
is lost, the refund is not sent again: the platform asks the app, which asks
bKash's refund status. When bKash's answer cannot be tied to the refund with
certainty, the refund is marked for manual review; check the payment in the
bKash merchant portal.

## Limits

- BDT only.
- No amount limits are declared to checkout. bKash sets per-transaction and
  daily limits per merchant account and per buyer wallet type (and refuses
  less than Tk 1); an amount outside them is refused when the payment is
  created, and checkout shows the payment as declined.

## Testing in the sandbox

Choose **Sandbox** and enter your sandbox credentials. bKash publishes sandbox
test wallets (numbers, OTP and PIN) in its developer documentation; pay with
one of those on bKash's sandbox page.

**Verification status:** the app is implemented against bKash's published
Tokenized Checkout v1.2.0-beta documentation and tested against a simulation
of that API (`src/index.test.ts`). It has not yet been run against bKash's
sandbox with real sandbox credentials; treat the live flow as verified against
the documentation only until that run is done.

## Intentionally not done

- **bKash webhooks (merchant notifications).** bKash delivers them through
  AWS SNS as certificate-signed messages; the app does not implement SNS
  signature verification and ignores webhook calls. That is safe: a Tokenized
  Checkout payment completes only when the merchant calls Execute, which this
  app does itself on the buyer's return, and the platform's status queries
  find any capture whose return was lost. A webhook would add no fact the app
  does not already get from bKash directly.
- **Agreements (saved wallets, mode 0000/0001).** Every payment is a one-off
  checkout (mode 0011).
- **Importing refunds made in the bKash merchant portal.**
